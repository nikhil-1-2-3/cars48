## 1. What the App Is — Tech Stack Summary

**RentHere / FleetFlow** is a full-stack car rental platform with two independently deployable services:

| Layer | Technology |
|---|---|
| **Frontend** | React 19, Vite 8, Tailwind CSS 4, React Router 7, Zustand, Framer Motion, Three.js/R3F, Axios |
| **Backend** | Node.js 20, Express 4, Prisma 6 ORM, PostgreSQL 16, JWT auth, Razorpay payments, Nodemailer, Google OAuth |
| **Database** | PostgreSQL 16 (Prisma schema with 8 models: User, Branch, Vehicle, Booking, Payment, Maintenance, RentalRecord, Review) |
| **Container runtime** | Docker (multi-stage Dockerfile for frontend; single-stage Node 20 Alpine for backend) |
| **Web server (frontend)** | Nginx Alpine — serves static Vite build, proxies `/api/` and `/uploads/` to backend |
| **Orchestration options** | Docker Compose (single-host, already configured) OR Kubernetes (k8s manifests present) |
| **CI/CD** | Jenkins pipeline (`Jenkinsfile` at root), targeting Docker Hub `singhnikhil212/` registry |

The frontend API client (`src/services/api.js`) reads `VITE_API_BASE_URL` at build time and falls back to the relative path `/api`, which the Nginx proxy handles — this means in the Docker Compose setup the frontend makes same-origin requests that Nginx proxies to the backend container on port 5000.

## 2. Required Environment Variables

### 2a. Backend — `backend/.env`

All values come from `backend/.env.example` (citation: `/home/nikhil-singh/projects/rent/cars48/backend/.env.example`).

| Variable | Required | Description | Where to get it |
|---|---|---|---|
| `PORT` | Yes | Server port (default `5000`) | Fixed, keep as 5000 |
| `NODE_ENV` | Yes | `production` for live deployments | Hardcode |
| `DATABASE_URL` | **Critical** | PostgreSQL connection string | See §3 Database Setup |
| `JWT_SECRET` | **Critical** | Secret for signing JWT tokens | Generate: `openssl rand -base64 64` |
| `JWT_EXPIRE` | Yes | Token expiry (e.g. `30d`) | Your preference |
| `GOOGLE_CLIENT_ID` | Yes (for Google OAuth) | OAuth 2.0 Client ID | [Google Cloud Console](https://console.cloud.google.com/) → APIs & Services → Credentials |
| `RAZORPAY_KEY_ID` | Yes (for payments) | Razorpay API key | [Razorpay Dashboard](https://dashboard.razorpay.com/) |
| `RAZORPAY_KEY_SECRET` | Yes (for payments) | Razorpay secret | Razorpay Dashboard |
| `EMAIL_HOST` | For OTP/email features | SMTP host (e.g. `smtp.gmail.com`) | Your email provider |
| `EMAIL_PORT` | For OTP/email features | SMTP port (usually `587` or `465`) | Your email provider |
| `EMAIL_USER` | For OTP/email features | SMTP username / email address | Your email account |
| `EMAIL_PASS` | For OTP/email features | SMTP password or App Password | Gmail: 16-char App Password |
| `FROM_EMAIL` | For OTP/email features | Sender address | Your choice |

> **Security warning:** The `docker-compose.yml` currently has `JWT_SECRET: supersecretcars48jwtkey12345` hardcoded in plaintext. **Change this before any production deployment.**

### 2b. Frontend — Build-time Vite env

The frontend reads one optional build-time variable (`src/services/api.js`):

| Variable | Required | Description |
|---|---|---|
| `VITE_API_BASE_URL` | No | Full URL to the backend API. If omitted, Nginx proxies `/api` to backend automatically. Only needed for cloud-separated deployments (e.g., `https://api.yourdomain.com`). |

For Docker Compose deployments, you do **not** need to set `VITE_API_BASE_URL` — the Nginx proxy handles it.

For cloud-separated deployments (Vercel frontend + Railway backend), set:
```
VITE_API_BASE_URL=https://your-backend-url.up.railway.app
```
This must be set at **build time**, not at runtime.

## 3. Database Setup

**Database:** PostgreSQL 16 (citation: `docker-compose.yml`, `backend/prisma/schema.prisma`)

**Schema models:** User, Branch, Vehicle, Booking, Payment, Maintenance, RentalRecord, Review — 8 models with full relational integrity.

**Migration approach:** The project uses `prisma db push` (not `prisma migrate deploy`). The `docker-compose.yml` startup command is:
```
sh -c "npx prisma db push && node seed.js && npm start"
```

This means:
- `prisma db push` syncs the schema directly to the database (good for development, acceptable for early-stage production).
- `node seed.js` seeds initial data (branches, sample vehicles).

**For production**, you should switch to `prisma migrate deploy` for proper migration history tracking. See §6 for notes on this.

**DATABASE_URL format:**
```
postgresql://USER:PASSWORD@HOST:5432/DBNAME?schema=public
```

## 5. Option A: Docker Compose on a Single VPS (Recommended)

This is the most pragmatic path. The `docker-compose.yml` is already fully configured.

### Prerequisites

- A VPS/VM running Ubuntu 22.04+ (DigitalOcean, Hetzner, Linode, AWS EC2 — minimum 2GB RAM recommended)
- A domain name pointed to your server's IP (A record)
- Docker and Docker Compose installed on the server

### Step 1 — Provision the Server

```bash
# SSH into your server
ssh root@YOUR_SERVER_IP

# Install Docker
curl -fsSL https://get.docker.com | sh
systemctl enable docker
systemctl start docker

# Install Docker Compose plugin
apt-get install -y docker-compose-plugin

# Create a non-root deploy user (recommended)
adduser deploy
usermod -aG docker deploy
```

### Step 2 — Get the Code onto the Server

```bash
# Option A: Clone directly
git clone https://github.com/YOUR_USERNAME/cars48.git /opt/cars48
cd /opt/cars48

# Option B: Push from CI/CD (see §7 Jenkins notes)
```

### Step 3 — Create the Production `.env` File

The `docker-compose.yml` reads `./backend/.env` via `env_file`. Create it on the server:

```bash
cd /opt/cars48
cp backend/.env.example backend/.env
nano backend/.env
```

Fill in the real values:
```env
PORT=5000
NODE_ENV=production
DATABASE_URL=postgresql://cars48_user:STRONG_PASSWORD_HERE@postgres:5432/cars48_db?schema=public
JWT_SECRET=<output of: openssl rand -base64 64>
JWT_EXPIRE=30d
GOOGLE_CLIENT_ID=YOUR_REAL_GOOGLE_CLIENT_ID
RAZORPAY_KEY_ID=rzp_live_XXXXXXXXXXXX
RAZORPAY_KEY_SECRET=YYYYYYYYYYYYYYYYYYYY
EMAIL_HOST=smtp.gmail.com
EMAIL_PORT=587
EMAIL_USER=your@gmail.com
EMAIL_PASS=your_16_char_app_password
FROM_EMAIL=noreply@yourdomain.com
```

> **Important:** The `DATABASE_URL` inside the `backend/.env` for Docker Compose must use hostname `postgres` (the Docker service name), not `localhost`.

### Step 4 — Fix the docker-compose.yml for Production

The current `docker-compose.yml` has hardcoded secrets that must be overridden. The `env_file: ./backend/.env` already covers most of them, but there are inline hardcoded values in the `environment:` block that take precedence over `env_file`. 

**You must remove or update these hardcoded lines in `docker-compose.yml` before deploying:**
```yaml
# REMOVE or change these in the backend service environment block:
JWT_SECRET: supersecretcars48jwtkey12345      # INSECURE — use env file instead
GOOGLE_CLIENT_ID: mocked_google_client_id      # Replace with real value
RAZORPAY_KEY_ID: mockedkey                     # Replace with real value
RAZORPAY_KEY_SECRET: mockedsecret              # Replace with real value
```

The cleanest fix: remove all the hardcoded `environment:` entries from the backend service and rely entirely on `env_file: ./backend/.env`.

Also change `NODE_ENV: development` to `NODE_ENV: production`.

### Step 5 — Set Up SSL with a Reverse Proxy (Nginx + Certbot)

The current setup exposes frontend on port `5174` and backend on `5002`. For production you need SSL and a clean domain. Install a host-level Nginx as a reverse proxy:

```bash
apt install -y nginx certbot python3-certbot-nginx

# Create Nginx server block for your domain
cat > /etc/nginx/sites-available/cars48 << 'EOF'
server {
    server_name yourdomain.com www.yourdomain.com;

    location / {
        proxy_pass http://localhost:5174;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
EOF

ln -s /etc/nginx/sites-available/cars48 /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

# Get SSL certificate
certbot --nginx -d yourdomain.com -d www.yourdomain.com
```

### Step 6 — Launch the Stack

```bash
cd /opt/cars48

# Build and start all services (detached)
docker compose up --build -d

# Watch logs
docker compose logs -f

# Check all containers are healthy
docker compose ps
```

Expected output: 4 containers running — `cars48_postgres`, `cars48_backend`, `cars48_frontend`, `cars48_studio`.

The startup command `npx prisma db push && node seed.js && npm start` will:
1. Push the Prisma schema to PostgreSQL
2. Seed initial data
3. Start the Express server

### Step 7 — Verify Deployment

```bash
# Backend health check
curl http://localhost:5002/api/health   # or whatever health endpoint exists

# Frontend
curl -I http://localhost:5174

# Prisma Studio (development only — disable in production!)
# Access: http://YOUR_SERVER_IP:5555
```

### Step 8 — Ongoing Operations

```bash
# Pull latest code and redeploy
cd /opt/cars48
git pull
docker compose up --build -d

# View logs for a specific service
docker compose logs -f backend

# Run a one-off migration
docker compose exec backend npx prisma db push

# Backup the database
docker compose exec postgres pg_dump -U cars48_user cars48_db > backup.sql

# Restore
docker compose exec -T postgres psql -U cars48_user cars48_db < backup.sql
```

## 6. Option B: Cloud-Separated Services

This approach puts the frontend on a static CDN host and the backend on a managed platform.

### Frontend → Vercel (or Netlify)

The Vite build (`npm run build`) outputs to `dist/`. Both Vercel and Netlify support this natively.

**Steps for Vercel:**

1. Push code to GitHub
2. Go to [vercel.com](https://vercel.com), import the repo
3. Set **Root Directory** to `frontend`
4. Build command: `npm run build`
5. Output directory: `dist`
6. Add environment variable:
   ```
   VITE_API_BASE_URL = https://your-backend.up.railway.app
   ```
7. Deploy

**Important:** When deploying to Vercel, the Nginx proxy doesn't exist. The frontend makes requests to `VITE_API_BASE_URL` directly. You **must** configure CORS on the backend to allow requests from your Vercel domain.

Add to your backend CORS configuration:
```js
origin: ['https://yourdomain.vercel.app', 'https://yourdomain.com']
```

### Backend → Railway (or Render)

**Steps for Railway:**

1. Create a new Railway project
2. Add a **PostgreSQL** plugin/service — Railway provides a managed PostgreSQL instance
3. Deploy backend service from GitHub, set root directory to `backend`
4. Start command: `npx prisma db push && npm start`
5. Set all environment variables in Railway's dashboard (use the variables from §2a)
6. Set `DATABASE_URL` to Railway's auto-provided PostgreSQL URL

**Steps for Render (alternative):**

1. Create a new Web Service, connect GitHub repo, root: `backend`
2. Build command: `npm install`
3. Start command: `npx prisma db push && npm start`
4. Add all environment variables
5. Create a separate PostgreSQL database on Render, copy the connection string to `DATABASE_URL`

### Backend → AWS EC2 + RDS (production-grade)

1. Provision RDS PostgreSQL 16 instance (Multi-AZ for HA)
2. Launch EC2 t3.small+, install Docker
3. Run just the backend container:
   ```bash
   docker run -d \
     --env-file ./backend/.env \
     -p 5000:5000 \
     singhnikhil212/renthere-backend:latest
   ```
4. Put an Application Load Balancer in front
5. Use ACM for SSL certificates

## 7. CI/CD Notes — Jenkinsfile Analysis

Citation: `/home/nikhil-singh/projects/rent/cars48/Jenkinsfile`

The Jenkinsfile defines a 4-stage pipeline:

| Stage | What it does |
|---|---|
| **Checkout** | `checkout scm` — pulls source from Git |
| **Build Docker Images** | Builds `singhnikhil212/renthere-frontend` and `singhnikhil212/renthere-backend` in parallel, tagged with `$BUILD_ID` and `latest` |
| **Push Docker Images** | Pushes both images and both tags to Docker Hub |
| **Deploy to Kubernetes** | Updates image tags in `k8s/*.yaml` manifests, runs `kubectl apply -f k8s/` |

**Known issues and TODOs in the Jenkinsfile:**

1. **`KUBECONFIG_CREDENTIAL_ID = 'your-kubeconfig-id'`** — this placeholder must be replaced with a real Jenkins credential ID before the deploy stage will work.
2. **`powershell` steps** — the Jenkinsfile uses PowerShell commands, meaning Jenkins is expected to run on Windows. If you're running Jenkins on Linux/Docker, replace all `powershell "..."` with `sh "..."`.
3. **No Docker Hub authentication step** — the pipeline comment says "Jenkins will use your credentials." For a proper CI setup, add a `withCredentials` block:
   ```groovy
   withCredentials([usernamePassword(credentialsId: 'dockerhub-creds', ...)]) {
       sh "docker login -u $DOCKER_USER -p $DOCKER_PASS"
   }
   ```
4. **Hardcoded kubeconfig path:** `C:\Users\nikhil singh\.kube\config` — clearly a local Windows dev machine path. Must be changed to use Jenkins credentials for production.
5. **The Kubernetes `backend-deployment.yaml` references a Kubernetes Secret** (`secretRef: name: renthere-secrets`) that does not exist in the `k8s/` directory. You must create this secret in your cluster before deploying:
   ```bash
   kubectl create secret generic renthere-secrets \
     --from-env-file=backend/.env
   ```
6. **No test stage** — there are no automated tests in the pipeline. Add a test stage before building images.
7. **No database migration step** — Kubernetes deployments don't include `prisma db push`. Add an init container or a pre-deploy Job to run migrations.

**Recommended Jenkinsfile fixes for production:**
- Add Docker Hub credential binding
- Replace `powershell` with `sh` on Linux Jenkins
- Create the `renthere-secrets` Kubernetes Secret as part of the pipeline or as a prerequisite
- Add a migration job/init container to the Kubernetes backend deployment

## 9. Recommended Deployment Path

For your current stage (active development, single developer, cost-conscious):

**Best immediate option: Docker Compose on a single VPS (Option A)**

- Then consider splitting frontend to Vercel/Cloudflare Pages for CDN benefits
- The Kubernetes/Jenkins path is already designed for that future state — the k8s manifests and Jenkinsfile are correct architecturally, they just need the credential gaps filled in
